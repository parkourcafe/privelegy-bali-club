# AI crawler access — can they fetch us at all?

> Read `otherbali-overlay.md` §6 first. Our robots.txt is generated by
> `app/robots.ts` and asserted by `app/robots.test.ts`. Never hand-write a
> `robots.txt` file, and read the measured current state before reporting a
> finding.

## Why this is step one

If AI crawlers are blocked, content quality is irrelevant — the page cannot
appear in an AI answer at any score. Upstream cites an Originality.ai 2025
study finding that over 35% of the top 1,000 websites block at least one major
AI crawler and 5–10% block all of them, usually inherited from legacy SEO
configuration rather than chosen. (Upstream's figure, unverified — overlay §8.)

## Our current state, measured

`app/robots.ts` emits, in production only:

```txt
User-agent: *
Allow: /
Disallow: /admin/ /partner/ /onboard/ /api/ /me /list/ /review
Sitemap: https://www.otherbali.com/sitemap.xml
```

There are **no AI-crawler-specific groups**. Under the robots.txt standard a
crawler whose user-agent matches no group falls back to `*`, so every crawler
in the tiers below is currently allowed to fetch every public page. Nothing is
blocked.

Outside production (`VERCEL_ENV !== "production"`) the route disallows
everything. A crawl check against a preview URL will report a fully blocked
site. That is intended — do not "fix" it, and do not run access checks against
preview deployments.

The open decision — whether to make the allowance explicit — is stated in
overlay §6 with its trade-off. It is not this file's to make.

## Crawler reference

### Tier 1 — powers AI search surfaces where users ask questions

| Crawler | Operator | Purpose | Blocking costs you |
|---|---|---|---|
| `GPTBot` | OpenAI | ChatGPT browsing, search; may be used for model improvement | Presence in ChatGPT Search |
| `OAI-SearchBot` | OpenAI | ChatGPT search only, **not** used for training | ChatGPT search results even if GPTBot is allowed |
| `ChatGPT-User` | OpenAI | Fetches when a user explicitly asks ChatGPT to visit a URL | Users who are actively trying to read you |
| `ClaudeBot` | Anthropic | Claude web search, citations, analysis | Claude's web search and URL analysis |
| `PerplexityBot` | Perplexity | Perplexity's sourced-answer engine | Perplexity results — and it always shows source links, so it is among the best AI referral sources |

All Tier 1: **allow**. There is no strategic case for blocking a search-only
crawler that attributes sources.

### Tier 2 — broader AI ecosystem

| Crawler | Operator | Note |
|---|---|---|
| `Google-Extended` | Google | Controls Gemini training and AIO improvement. **Does not affect Google Search rankings** — that is Googlebot. Blocking it does not remove you from AI Overviews, which draw on standard indexing. |
| `GoogleOther` | Google | Non-ranking research and one-off crawls. |
| `Applebot-Extended` | Apple | Apple Intelligence. Distinct from `Applebot`, which powers Siri and Spotlight and is unaffected. |
| `Amazonbot` | Amazon | Alexa answers, Amazon AI. Voice-search relevance. |
| `FacebookBot` | Meta | Meta AI. Link previews use a different crawler and are unaffected. |

All Tier 2: **allow**. Low risk, and the Google-Extended distinction is the one
most often got wrong — people block it fearing a ranking hit that does not
exist.

### Tier 3 — training-only, no live-search impact

| Crawler | Operator | Recommendation |
|---|---|---|
| `CCBot` | Common Crawl | Context-dependent. Feeds many models' training sets; affects no live product. |
| `anthropic-ai` | Anthropic | Context-dependent. Training only; Claude's live features are `ClaudeBot`. |
| `cohere-ai` | Cohere | Context-dependent. Low priority. |
| `Bytespider` | ByteDance | Upstream recommends **block** for Western-market sites — aggressive crawling, little visibility benefit. Allow if targeting Chinese/Asian markets. |

Bytespider is worth an actual decision for us rather than a default: Other Bali
serves an international tourist audience including Chinese and Korean speakers,
and the repository already ships Chinese and Korean UI chrome. Upstream's
"block it, you're Western" reasoning does not transfer cleanly. Leave it under
`*` unless someone measures a crawl-load problem.

## What to check

1. **Fetch the live production robots.txt.** `curl -s https://www.otherbali.com/robots.txt`.
   Read what is served, not what you expect `app/robots.ts` to produce.
2. **Resolve each crawler against it.** For each user-agent, find the matching
   group — or confirm it falls back to `*`. Longest matching user-agent token
   wins; there is no group inheritance.
3. **Check meta and headers too.** robots.txt is not the only block. Look for
   `<meta name="robots">` and `X-Robots-Tag` response headers. Our `/v/`
   redemption pages carry a deliberate `noindex` and must stay crawlable so
   engines can read that directive — blocking them in robots.txt would strand
   legacy URLs, which is why `app/robots.ts` says so in a comment.
4. **Verify a real fetch.** A permissive robots.txt does not prove reachability.
   Request a page with a crawler user-agent and confirm a 200 with content:

   ```bash
   curl -sS -A "Mozilla/5.0 AppleWebKit/537.36 (KHTML, like Gecko; compatible; GPTBot/1.2; +https://openai.com/gptbot)" \
     -o /dev/null -w '%{http_code}\n' https://www.otherbali.com/canggu
   ```

   A CDN or WAF rule can block a bot that robots.txt welcomes. That failure is
   invisible in robots.txt and is the one worth actually testing.
5. **Confirm the sitemap line resolves.** `app/robots.ts` advertises
   `https://www.otherbali.com/sitemap.xml`; check it returns 200 and lists
   current URLs.

## Changing it

Edit `app/robots.ts`. Update `app/robots.test.ts` in the same commit — it runs
in the default `npm test` list, so a change without a test update fails the
suite. Keep the production/non-production branch intact.
