## 2. Замер разрыва (шаг 1 playbook’а: что в базе vs что доходит до страницы)

Из `production-editorial-diagnostic-2026-08-12.csv` (1272 строки, все
`active` + `published`):

| Метрика | Значение |
|---|---|
| Active + published Place Pages | **1272** |
| Проходят **боевой** гейт публикации (`why_its_here` И `best_for` непустые) | **1272 / 1272** |
| Проходят **release-гейт** (более строгий редакционный бар) | **480 / 1272** |
| Не проходят release-гейт | **792** |

Разбивка по первичному классу очереди:

| Класс | Строк | Смысл |
|---|---:|---|
| `P1_REWRITE_BOILERPLATE` | 433 | живая, но шаблонная `why`/`best_for` |
| `P1_ADD_VERIFIED_ANCHOR` | 359 | нет проверенного ценового/решающего якоря |
| `P2_ADD_NOT_FOR` | 234 | нет `not_for` |
| `READY_FOR_RELEASE_GATE` | 144 | уже хороша |
| `P2_DEEPEN_PRACTICAL_VALUE` | 95 | тонкая практическая ценность |
| `P2_VERIFY_SOURCE_AND_DATE` | 7 | перепроверить источник/дату |

**Важно про два гейта.** Боевой гейт (`lib/publication.ts`) — это двухполевой
`hasText(whyItsHere) && hasText(bestFor)`; его проходят все 1272. Release-гейт
(480/1272) — это **более строгий, предлагаемый** редакционный бар; SQL, который
его считает, в репозитории нет — снапшот и есть его выход, снятый разово с базы.
Глобально этот гейт **не включаем** (запрет владельца: не поднимать глобальный
SEO-гейт). Он служит только приоритизацией внутри очереди переписывания.

## 3. Почему старый Batch 01 дал ноль обновлений (исправленное объяснение)

**Было (неверно):** «батч целил только в пустые `why_its_here` / `best_for`, а
таких не осталось».

**Стало (верно):** старый Batch 01 защищал каждый `UPDATE` **exact-old guard’ом**
— условием `WHERE`, требующим, чтобы текущие значения совпадали с теми, под
которые батч был написан, сразу по нескольким полям: редакционные тексты,
`price_anchor` и `last_verified_at`. Это оптимистическая блокировка от
затирания. **Ноль обновлённых строк означает, что предикат guard’а не совпал ни
в одной строке** — значит, хотя бы одно из защищённых полей уже держало не то
точное значение, что в снапшоте батча (дрейф данных между снятием снапшота и
применением).

Это НЕ про пустоту полей. Подтверждение прямо в снапшоте:

- **Все 1272 строки проходят двухполевой гейт** (`has_why` = true и
  `has_best_for` = true у 100% строк). Пустых `why`/`best_for` среди
  active+published просто нет — значит «целились в пустые» не может быть
  причиной.
- **`last_verified_at` крайне волатилен.** В инвентаре десятки разных дат:
  2026-07-28 у 641 строки, но также крупные кластеры 2026-08-07 (137),
  2026-07-29 (108), 2026-08-08 (94), 2026-08-04 (76), 2026-07-30 (57)… Поле
  переписывалось волнами. Любой батч, снявший снапшот до такой волны, получает
  разъехавшийся guard по `last_verified_at` разом на всех строках → 0 совпадений.
- `price_anchor` заполнен лишь у 467/1272 — тоже подвижная поверхность, ещё один
  вход для рассинхрона.

**Вывод для перезапуска:** guard должен защищать **только то поле, что реально
переписывается**, а не пакет из текста + `price_anchor` + `last_verified_at`.
Канонический шаблон (`otherbali-data-ops-run/assets/apply-TEMPLATE.sql`) guard’ит
по совпадению `slug` + `status='active'` + `publication_status='published'` и по
целевому столбцу — и **сознательно не трогает `last_verified_at`** при
редакционном переписывании (иначе портится `lastmod` в sitemap и строка «Last
checked»). Именно так сделан эталонный `aug-import-editorial` батч.

## 4. Метод очереди (все пять сигналов)

`build_queue.py` присоединяет GSC Pages к диагностике по нормализованному
`/places/<slug>` и считает прозрачный композит:

- **спрос (GSC):** impressions (лог-шкала) · clicks · position (бонус за
  striking distance 5–15 из `docs/gsc-setup.md`);
- **редакционный долг:** тяжесть по классу очереди;
- **близость к release-гейту:** меньше оставшихся блокеров = ближе = быстрее win.

Веса: с GSC — `demand 0.50 · editorial 0.30 · proximity 0.20`; без GSC —
интерим `editorial 0.60 · proximity 0.40` (спрос отсутствует, перенормировка).
Ничего произвольного вроде «312» — очередь считается из сигналов.

## 5. Блокер: GSC Pages export не пришёл

Playbook, шаг 2: **приоритизация по трафику, не по алфавиту** — сначала районы с
публичными страницами и уже ранжирующиеся строки. Это и есть GSC-слой. Без него
интерим-очередь тянет наверх «быстрые якоря», а не боилерплейт с реальным
спросом (видно в `out/queue-editorial-interim.csv`: топ занят
`P1_ADD_VERIFIED_ANCHOR`, потому что у них выше близость к гейту, а спрос не
участвует). Это провизорно и **должно быть пересчитано под GSC** до фиксации
состава Batch 01.

Что нужно: экспорт **GSC → Результаты поиска → Страницы** (CSV) за 3 месяца
(колонки: `Top pages`/`Page`, `Clicks`, `Impressions`, `CTR`, `Position`).
Построитель принимает обычные варианты заголовков и джойнит только `/places/*`.

Как только файл на месте:
```
python3 build_queue.py --gsc inputs/gsc-pages-export.csv
```
→ `out/queue-composite.{csv,json}` — финальная очередь, из вершины которой
нарезается Batch 01.

## 6. План Batch 01 (после GSC) — по эталону `aug-import-editorial`

1. Взять верх composite-очереди (класс `P1_REWRITE_BOILERPLATE` в приоритете —
   живой боилерплейт с доказанным спросом).
2. Собрать факты по каждому заведению с **официальных** источников (сайт/бронь/IG),
   формат сдачи — `slug,value,source_url,source_type,status,note`; строка без
   `source_url` не принимается; not_found-строки тоже в ведомость (source ledger).
3. **Приёмка построчно** по `references/acceptance-rules.md` — статус коллектора
   не доказательство. Отклонённые строки — в отдельный список с причиной.
4. Сгенерировать guarded UPDATE по `assets/apply-TEMPLATE.sql`: dry-run одной
   строки, join по `slug`, `status='active' AND publication_status='published'`,
   ожидаемый count в комментарии, блок отклонённых в конце. `last_verified_at`
   при чистом переписывании текста — не трогать.
5. Перед любым apply — пройти `otherbali-supabase-write` (на проде есть
   constraint, которого нет ни в одной миграции репо; dry-run — единственная
   надёжная проверка).

**Оговорка (Refusals playbook’а):** `best_for` и `not_for` — поля, которые нельзя
переписывать «правдоподобно». Если по заведению нет источника — поле остаётся как
есть/null, строка идёт в отклонённые, а не выдумывается.
